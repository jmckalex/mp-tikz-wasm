# 09 — Testing and conformance

## 1. The oracle principle

Every graphical expectation is generated by **real `mpost` from the pinned TeX
Live**, never hand-written. Golden files carry a header recording the oracle
version; CI regenerates them when the pin moves and the diff is reviewed by a
human. This is the only way to know a WebAssembly build of a 40-year-old
numerical program is correct.

```
test/golden/
  <case>.mp
  <case>.expected.eps        # from `mpost` (prologues=0, deterministic)
  <case>.expected.svg        # from `mpost -s outputformat=svg -s prologues=3`
  <case>.expected.json       # from our own backend, reviewed once
  <case>.oracle              # "TeX Live 2025 / MetaPost 2.11"
```

## 2. Test layers

### L0 — the native contract harness

`test/contract/` builds `reference/host_shim_reference.c` **natively** (not
wasm) against the vendored sources and asserts every CONTRACT in
`docs/04`:

* `mem_name = NULL` is rejected before it can crash;
* `find_file` is called for `input`-ed files;
* `read_ascii_file` must return `malloc`ed memory (assert with a poisoned
  allocator);
* `read_binary_file` fills the caller's buffer and sets `*size`;
* non-interactive mode overrides the I/O callbacks (assert ours are *not*
  called);
* `ship_out` is reset per figure (ship two figures, assert you get the second);
* `make_text` return values are parsed as MetaPost source;
* `mp_execute` terminates the job.

This runs in seconds, has no wasm in the loop, and is where you find out that a
TeX Live bump changed the API. **Write it first, at M0.**

### L1 — unit tests

TypeScript, vitest. The scanner, the `.mpx` splitter, the cache keys, the
diagnostics parser, the `find_file` search order, the CLI argument parser.
Pure functions, no wasm.

### L2 — golden graphics

For each case, compile with mp-tikz-wasm and compare:

* **EPS**: normalise the `%%CreationDate` and `%%Creator` lines, then compare
  **byte for byte**. MetaPost's PostScript output is deterministic to the last
  digit; anything else is a bug. Do not introduce a tolerance — a tolerance
  hides exactly the numerical drift you are testing for.
* **SVG**: same, after normalising the creation comment.
* **JSON**: structural compare with an exact numeric equality.

Corpus, at minimum:

| Group | Cases |
| --- | --- |
| Primitives | every path construction operator; `..`, `---`, `&`, tension, curl, controls, `cycle` |
| Pens & strokes | `pencircle`, `pensquare`, transformed pens, `dashed`, `withpen`, line caps/joins, miter limits |
| Fills | `fill`, `unfill`, `filldraw`, even-odd vs nonzero, `buildcycle` |
| Colour | grey/RGB/CMYK, `withcolor`, transparency via `withprescript` |
| Clipping & bounds | `clip`, `setbounds`, nested |
| Text tier 0 | `label`, `dotlabel`, `thelabel`, all suffixes, `infont`, `scaled`, `rotated` |
| Text tier 1 | `btex` with plain TeX: text, math, boxes, rules |
| Text tier 2 | LaTeX: amsmath, arrays, `\parbox`, font changes, custom macros |
| Macro packages | `boxes.mp`, `graph.mp`, `format.mp`, `sarith.mp`, `mfplain.mp` |
| Number systems | the same figure in scaled / double / decimal; assert the *documented* differences |
| Errors | 30+ deliberately broken files; assert the diagnostic, not just failure |
| Regressions | one file per fixed bug, named after the issue |

Harvest real MetaPost in the wild for the corpus — the `metapost` examples in
TeX Live (`metaobj`, `featpost`, `metauml`, `cmarrows`) are excellent stress
tests and are already installed with the oracle.

### L3 — `mptrap`, the official conformance suite

TeX Live ships `mptraptest.test` and the `triptrap/` data. This is MetaPost's
equivalent of Knuth's `trip` test: a deliberately pathological input that
exercises arithmetic edge cases, error recovery and the log format.

Run it against `mplib.wasm` and diff `mptrap.log` against `trap.log` from the
oracle. **This must pass before M8 closes.** Expect it to find real bugs in the
shim — particularly around integer overflow behaviour and `scaled` arithmetic,
which is where a wasm/x86 difference would show up.

Caveat: `mptrap` exercises interactive and file-based paths. You may need a
harness mode that uses `extensions=0` and file input to run it faithfully; that
is a good reason to keep the classic path working (`docs/05` §7).

### L4 — end-to-end

Playwright against a real browser (Chromium, Firefox, WebKit): load the demo
page, compile, assert the DOM contains the expected `<path>` count and the SVG
matches the golden. Also run with cross-origin isolation **off** to prove the
sync-XHR fallback works.

Node tests run the CLI as a subprocess against a fixture directory.

### L5 — fuzzing

MetaPost's scanner is a good fuzz target and a crash in wasm is a security
issue for anyone running untrusted input.

* `libFuzzer`/AFL++ against the **native** build of `mp.c` + the shim, with
  ASan and UBSan. This is where you find the real memory bugs; wasm hides them.
* A grammar-aware fuzzer for MetaPost source, seeded from the corpus.
* A byte-level fuzzer for `.tfm`, `.pfb` and `.dvi` parsing — all three read
  untrusted binary input, and `dvitomp` in particular parses attacker-supplied
  DVI if a user compiles someone else's document.
* Assert: no crash, no hang beyond the timeout, no OOM below the limit.

## 3. Differential testing

The highest-value test in the project: a script that takes any `.mp` file,
compiles it with both the oracle and mp-tikz-wasm, and diffs. Point it at
every `.mp` in `texmf-dist/metapost/` (about 20 MB of real-world MetaPost,
including `profcollege`, `metaobj`, `featpost`, `mcf2graph`) and triage the
differences.

```sh
scripts/difftest.sh /usr/local/texlive/2025/texmf-dist/metapost/**/*.mp
```

Expect a long tail: missing bundle files, troff-mode files, files needing
packages. Each triaged failure becomes either a bundle recipe entry, a
documented limitation, or a bug.

## 4. Performance regression tests

Track and fail the build on regressions beyond a threshold:

* cold start (module instantiation + `plain.mp` parse);
* warm compile of a 200-line figure, no text;
* warm compile with 40 `btex` blocks, cold cache;
* the same, warm cache;
* peak wasm memory for each.

Publish the numbers in the README. They are the honest answer to "is this fast
enough for a live editor?"

## 5. CI matrix

| Axis | Values |
| --- | --- |
| OS | ubuntu-latest, macos-latest |
| Node | 20, 22, latest |
| Build | release (`-O3 -flto`), debug (`-O0 -sASSERTIONS=2 -sSAFE_HEAP=1`) |
| Number system | scaled, double, decimal |
| Browser (L4) | chromium, firefox, webkit |

The debug build runs L0–L3 nightly, not per-commit — `SAFE_HEAP` is slow but it
is the thing that catches shim bugs before users do.

## 6. What "done" looks like

* `mptrap` passes.
* The differential run over `texmf-dist/metapost/` has zero *untriaged*
  differences.
* The golden corpus is byte-identical for EPS and SVG.
* Fuzzing runs 24 h with no crash.
* The performance table in the README is real, measured, and dated.
